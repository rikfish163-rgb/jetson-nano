| 停车原因 | 指令区间累计时间 |
| --- | ---: |
| `scan_missing_or_stale` 雷达数据不满足时效要求 | 3.54 秒 |
| `lane_stream_stale` 巡线数据超时 | 1.59 秒 |

巡线性能日志从约 9 FPS / 108.61 毫秒每帧，降到 5.91 FPS / 168.34 毫秒每帧；最后一组白线处理约 57.76 毫秒、中心线置信度计算约 49.67 毫秒。感知耗时与命令更新间隔均显示处理链路存在延迟。

本次录制正常关闭，记录队列丢弃数为 0，未因空间或容量限制提前结束。该统计只说明录制器收到的数据完整，不说明摄像头或雷达原始输入没有丢帧。

## 结论与边界

反复停走存在明确的软件原因：感知数据超过时效门限，控制器置零；新数据满足条件后恢复前进。此外，上游命令更新超时也触发停车。优先排查处理耗时、调度与消息排队。

目前没有原始 `/scan` 到达时间、包序号和实测车速，不能断言雷达硬件持续丢包，也不能排除机械或低速动力方面的附加问题。控制指令的 43 个区间不等于实测车辆恰好停了 43 次。不能仅靠放宽超时、关闭雷达或增加卡尔曼滤波来证明卡顿已解决。

后续静态诊断应同时记录原始扫描到达时间、扫描完成时间、处理完成时间、控制指令发布时间，区分输入断流、处理积压和命令延迟；降低感知耗时后再做实车确认。
